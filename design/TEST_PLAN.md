# 検証手順

## 今回のひな形
- HTTP配信で出店者2組、頒布物4点、ブース番号が表示される。
- 「朝の窓」で1組、「短歌」でジャンルを絞って1組になる。
- 存在しない検索語は0件の案内になる。
- 画面幅390pxで横スクロールせず、入力欄・本の情報が読める。
- JSON読込失敗時はエラー案内になる。
- サンプルJSONに連絡先・認証情報がない。
- GAS配置・設定後にGASとSheetsの疎通成功が表示される。
- 設定不足やログイン前の保存要求は拒否される。

## 本人限定保存の合格条件（コード実装済み・実環境で一部確認済み）
- 保存・再読込後にプロフィールと複数頒布物が一致する。
- 他者のプロフィール・作品の読取（非公開部分）・更新・削除を拒否する。
- 無効・期限切れ・失効したセッションで編集できない。
- 古い画面の保存は競合として拒否し、既存内容を変えない。
- 同じ保存要求の再送で更新番号や新規頒布物を二重に作らない。
- 同じ要求IDに別内容を載せた操作を拒否する。
- コード再利用・期限切れ・5回誤入力・再送前のコード・宛先変更後の旧コードを拒否する。
- 許可外の宛先には送信せず、再送間隔・回数制限を守る。
- メール失敗やGoogle割当不足で、既存プロフィールやログイン情報を壊さない。
- ソース、Sheets、ログ、ブラウザーURLにコード・セッショントークンの原文を残さない。
  コード原文は送信メールと利用者の入力欄、トークンはログイン応答とブラウザーのメモリーにのみ必要。

## ローカル自動テスト

実行: `node --test tests/gas.test.mjs`

実際の.gsをNode.js VMで実行し、SpreadsheetApp・MailApp・PropertiesService・Utilities・
LockServiceを代替する。Googleに接続せず、実メールも送信しない。
本人限定の読取・保存、所属変更時の拒否、コード・セッション、競合、再送、
保存前失敗と保存後応答喪失、入力検証、初期設定の再実行を確認する。
同時保存については同じ更新番号の2要求とロック取得失敗を検証するが、
Googleの実際の並行実行・flush・権限・割当の挙動はこのテストでは証明しない。

## ブラウザーの模擬環境

`node tests/serve-experiment.mjs` で http://127.0.0.1:8081/ を開く。
宛先 `a@example.invalid` / `b@example.invalid` の模擬コードが画面上部に出る。
上部の「次の保存応答を失わせる」で、保存成功後の通信失敗からの再送を試せる。
これは実験用本体には含まれないローカル検証用の仕組み。

確認する操作:
1. 接続確認 → コード送信 → コード入力 → ログイン。
2. 出店名・紹介文・頒布物2点を入力し保存。再読込で一致する。
3. 1点を編集し、もう1点を削除して保存。再読込で確認する。
4. 応答喪失を設定して保存。入力が固定され、同じ要求の再送で1回だけ保存される。
5. 未保存のまま読直し・ログアウトすると確認が出る。ログアウト後は編集内容を表示しない。
6. A・Bを別のブラウザーで操作し、内容が分離している。幅390pxでも入力・保存できる。
7. HTMLとして解釈される文字列を紹介文に入れてもスクリプト実行や要素追加が起きない。

## Google上で追加する試験

- 自分のみアクセスの /exec で実メール受信、本人確認、保存、Sheets内容、再取得を確認する。
- A・Bを別のGoogleアカウント／ブラウザーで開き、本人限定操作を確認する。
- 開発者ツール等からAのセッションでBの出店者ID・頒布物IDを送っても拒否される。
- セッション失効、Users/Membershipsの停止、コード再送・期限を実際に確認する。
- 同じ更新番号から2保存を実行し、一方だけ成功することを確認する。
- 通信切断後の再送、メール失敗時の案内、Sheets書込不能時の案内を確認する。
- 実行ログに確認コード・メール本文・トークン・自由入力を残していないことを確認する。
- 4シートへのアクセスを出店者に共有していないことを確認する。
