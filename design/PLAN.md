# 経緯と問題、実装方針

## 経緯と問題
既存KHBの本番運用から分離して、即売会の申込・出店者編集・カタログ公開を検証する。
本repo作成の依頼は最小構成の作成。既存本番の変更・デプロイは行わない。

## 現在の構成
docs/ のカタログは架空JSONを表示する。gas/ は疎通確認用のみ。
出店者を切り替えるUI等を認証の代わりには設けない。

## 試作上の仮置き
- 公開はGitHub Pages、編集画面は別URLのGAS HTML Service。
- 原画像は非公開Drive、業務データは専用Sheetsを候補とする。
- 公開は運営が確認して手動実行する方式を最初に試す。
- 本人確認はメール確認コードを第一候補とする。
いずれも本番仕様の確定ではない。

## 次の実装順序
1. 固定ID、セッション、期限・失効、出店者への所属を設計する。
2. プロフィール・複数頒布物を保存し、他者ID指定の更新・削除を拒否する。
3. 画像の受信、実ファイル検証、非公開保存、差替えを検証する。
4. 許可項目だけで公開JSONを生成し、公開画像と一緒に版管理して配信する。
5. 申込、選考・入金・配置・公開の独立した状態管理を追加する。

## データ設計
開催回、出店者、利用者と所属、申込、開催回別の出店プロフィール、
頒布物、開催回別出品、画像、セッション、公開版、変更履歴を分ける。
行番号を主キーにしない。更新番号による競合検知と再送の冪等性を持たせる。
公開データへ代表者名・メール・入金・内部メモ・認証情報を出さない。

## 未決定
開催日・会場・出店数・選考・決済・共同編集・画像制限・公開タイミング。
B案（静的画面＋API）、iframe、Cloudflare、Supabaseを候補として維持する。
GitHub Pagesの商取引に関する利用制限への適合性は、本番化前に再評価する。

## KHBからの流用候補
参照元: kleaex.github.io/khb2027/
- js/emailAuth.js、gas/khb2027_webapp.gs: コード期限・再送制限・本人確認の参考。
- gas/khb2027_webapp.gs: 保存後のメール失敗分離、ロック、履歴の参考。
- js/confirmGas.js: 通信失敗や再送時の表示の参考。
本ひな形にはKHBコード・設定・接続先をコピーしていない。
HTML Service化する際は内部関数を末尾 _ にし、公開入口ごとに認証・権限を検証する。
既存の名前＋メールによる照合を、そのまま恒久的な出店者IDに使わない。
